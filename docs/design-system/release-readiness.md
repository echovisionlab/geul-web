Review actual pages, views and features in order. Prepare semantics and interaction while preserving the existing design and copy within each accessibility change. Actual macOS VoiceOver and Linux Orca integration remains a separate later stage.

Baseline date: 2026-10-11. Current source registers **118 pages**, **140 visual entrypoints**, **12 query editor branches** and **12 additional tab/preview/share branches**. Review **54 Core families**, **70 feature contracts**, **17 body-block kinds**, **22 page-section kinds** and **10 form-field kinds** separately. Dynamic IDs, slugs and authored data are reviewed by applicable view structure/state, not an infinite inventory of individual URLs.

Detailed N/R/V/O/K/A/S/D/B states are in the [JSON matrix](./release-readiness.json); saved results use stable row IDs in the [review store](./release-readiness-reviews.json). ## Saved verification record

These statements and row notes preserve an earlier run. They are not a fresh result for later source changes; current review evidence must identify its source and execution conditions.

- The saved full-build record inspected 230 Storybook files and 1,244 states with Chromium play/axe: 1,219 passed, 25 failed, none skipped. This does not establish complete accessibility preparation.
- The recorded failures were 8 dangling notification IDREFs, 7 target-size failures, 3 contrast failures, 6 inline-link distinction failures and 1 unnamed math-block command. SourceEditor contrast was also detected in an earlier full run and remains a recheck item.
- Six account scenarios per Korean/English locale and four actual 390×844 mobile-list cases were checked separately. Actual VoiceOver/Orca speech and full-screen pixel comparison were not run.
- Story existence, source type checks and passing axe results do not establish every page semantic, reading order, state or user scenario.

## Change boundaries

- Do not arbitrarily change visible text, button/field labels, placeholders, tooltips, dates, numbers, units, filenames, language codes or translation keys solely to add accessibility semantics.
- Do not arbitrarily change layout, order, size, spacing, density, colors, icons, emphasis or design tokens. Consume existing Core/theme contracts; separately authorized visual work is reviewed at those owners.
- Supply needed names, descriptions, groups, relationships and states at the semantic layer. Do not put everything into one long aria-label or ban aria-label entirely. Preserve visible-label wording in accessible names.
- When aria-label replaces descendant content in a role's name, check whether meaningful content becomes inaccessible. Do not add names or tabIndex to every paragraph or generic container.
- Do not add a general a11y-off option for required semantics or interaction. Decoration and context-specific optional announcements use explicit contracts.
- ARIA does not fix contrast, focus visibility, obstruction or target geometry. Record the defect and design impact at the shared owner and review visual changes in the authorized scope.
- Do not invent UI, commands or steps for review convenience. Recording creation inside the app and uploading a recording file are separate features.

Follow the page/branch order below. For each row: **identify actual controls → check name/role/relationships/value → check order/keyboard → check data/permission states and transitions → compare the screen under identical conditions → connect Storybook regressions**. A shared-component correction does not replace per-page target names, columns, permissions and transition checks.

## Gates for every row

| Gate | Area                                  | Required preparation                                                                                                                                                          |
| ---- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| N    | Name and target                       | Identify each control's purpose and target. Supply necessary names and preserve visible label wording. Do not hide identifying information only in a description.             |
| R    | Role and relationships                | Expose roles matching actual interactions and relationships among headings, labels, descriptions, errors, groups and panels. Distinguish decoration from meaningful content.  |
| V    | Value and state                       | Values, selection, checked, expanded, read-only, disabled, required, invalid and progress states match actual data and permissions.                                           |
| O    | Reading and navigation order          | Provide meaningful document titles, landmarks, heading hierarchy and content order for structural navigation. CSS position alone does not establish reading order.            |
| K    | Keyboard and focus                    | Every offered command has a keyboard path. Focus is appropriate after entry, changes, deletion and close; editor selection is preserved.                                      |
| A    | Transitions and announcements         | Communicate progress, success, failure and empty results when needed. Avoid unnecessary focus movement, duplicate announcements and excessive progress updates.               |
| S    | State reproduction                    | Reproduce applicable data, permissions, errors and transitions with typed local inputs and outputs connected to production UI.                                                |
| D    | Visual and existing-copy preservation | Do not arbitrarily change visible copy, translation keys, placeholders, tooltips, date/number/unit/filename formatting, tokens, layout, density, colors, icons or sizes.      |
| B    | Storybook and regression              | Distinguish a rendered screen from verified semantics and interaction. Assert names, roles, states, order, focus and transitions; review axe findings and incomplete results. |

Document reading order, Tab order, the VoiceOver navigation cursor and text insertion/selection cursors are separate contracts. ARIA snapshots and DOM-focus checks are not actual screen-reader speech verification. Inspect UI and document-content languages separately.

## State and presentation combinations

| Axis         | Applicable combinations                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| Data         | Initial, normal, empty value/result, partial data, long values, loading, error and retry.                                      |
| Permissions  | Applicable signed-out, user, author/owner, administrator, read-only, disabled and revoked-permission combinations.             |
| Interaction  | Default, focus, selected, expanded, menu/dialog open, pending, success, failure, cancel and undo.                              |
| Presentation | light/dark, Korean and supported locales, content/mixed languages, RTL, narrow/medium/wide viewports, zoom and reduced motion. |
| Output       | Actually offered editor, preview, public, shared, print and conversion outputs.                                                |

First identify real data, permission and transition combinations, then define semantics and operation for each. Check narrow/wide layouts and light/dark on each actual View; other languages, RTL and zoom include long labels/values, hidden panels and layout boundaries. Typed local fixtures/transports reproduce server states. Provider and OS file-picker boundaries separate local UI preparation from actual integration checks.

## Conditions for completing a row

- Check every applicable N/R/V/O/K/A/S/D/B gate at both owner and actual consumer. Explain Not applicable with an actual absent product feature.
- Reproduce applicable states, including failure/retry/cancel, in Storybook and assert expected semantics, values, states, order, focus and outcomes. Do not invent UI for impossible state combinations.
- Preserve the existing copy, formatting and design under identical conditions within accessibility-only work. Track accessibility and visual review separately; unresolved screen impact keeps the row open.
- Axe alone does not complete a row. Inspect ambiguous names, relationships, keyboard paths and data alternatives in actual code/interaction.
- Keep actual VoiceOver/Orca checks separate. Prepared implementation is not completed assistive-technology verification or legal certification.

Use stable JSON matrix IDs as keys in the review store's rows. Record pending, in-progress, needs-fix, checked or not-applicable for N/R/V/O/K/A/S/D/B. Connect exceptions and fixes to actual code/work. Source or presentation-condition changes require affected checks to return to Pending. Do not add audit-only instructions or UI to production screens.
