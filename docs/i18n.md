# Translations (i18n)

## English is the source of truth

`messages/en.json` defines every UI message key. The other 19 files in `messages/` are
translations of it and must have exactly the same keys.

- **Types.** `global.d.ts` augments next-intl's `AppConfig.Messages` with the type of
  `messages/en.json`. `pnpm typecheck` rejects an unknown namespace or key in
  `useTranslations`, `getTranslations` and `t(...)`, including template-literal keys whose
  parts are typed unions. A cast (`as never`, `as any`) bypasses this, so do not use one for keys.
- **Adding or changing copy.** Edit `messages/en.json` first. Add the translations through
  Weblate, or edit the locale files directly, then run `pnpm i18n:sync-weblate --check` (needs
  `WEBLATE_API_TOKEN`) to compare the local files with Weblate. Never add a key to a locale
  file that English does not have, and never fill a missing translation with invented copy.
  If translations are not ready, the check fails and lists the missing keys.
- **Removing copy.** English is the source, so a key that no code reads is deleted from
  `messages/en.json` and from every locale file in the same change (the parity check fails
  otherwise). Remove the key from English, then run
  `node scripts/i18n/check-messages.mjs --prune` to remove it from every locale. Do not keep
  unused keys "for later" and do not delete a key from a locale file only. Weblate still has
  the deleted keys until the next sync: `pnpm i18n:sync-weblate --check` lists them as
  `remote_only`, and the next `pnpm i18n:sync-weblate` run (a replace upload of the local
  files) deletes them from Weblate. If the same change also edits existing translations
  locally (outside Weblate), that run reports `changed_values` and needs `--allow-value-drift`.
- **Proving a key is unused.** `pnpm typecheck` (and `pnpm storybook:typecheck` for stories)
  fails when a removed key is still used through a typed `t(...)`, `t.rich`, `t.markup`,
  `t.raw`, `t.has` or a typed catalogue read such as `useMessages().errorPage`. Before you
  delete a key, also rule out what the types cannot see: keys built from `string` values or
  behind a cast (`as never`, `as unknown as …`), namespaces read as a whole object and passed
  through a widened type, and copy consumed outside TypeScript (scripts, fixtures).
  `scripts/i18n/audit-unused-translation-keys.mjs` automates the type check per key group, but
  it refuses to run while the codebase has such unproven translator or catalogue flows.

## `pnpm i18n:check`

CI runs this in the "Build and static checks" job. `pnpm test` runs the same catalogue check
in `lib/i18n/message-catalogue-parity.test.ts`. It runs `scripts/i18n/check-messages.mjs`,
which fails when:

1. A locale is missing a key that English has, or has a key that English does not have.
2. A message does not parse as ICU MessageFormat.
3. The ICU structure differs from English: argument names, `number`/`date`/`time`/`select`
   formats, `select` option keys, or rich-text tag names (`<link>`, `<strong>`).
4. A translation drops English plural branches (writes `{count}` where English has
   `{count, plural, ...}`) in a language with CLDR plural forms. Languages with only the
   `other` category (ja, ko, zh, th, vi, id) may use a plain `{count}`. A translation may also
   add plural branches where English has none.
5. A `plural` or `selectordinal` (in any locale, English included) lacks a CLDR category of its
   language, as reported by `Intl.PluralRules(locale).resolvedOptions().pluralCategories`
   (`{ type: 'ordinal' }` for `selectordinal`). For example: ar `zero one two few many other`;
   pl and ru `one few many other`; fr, es, it and pt `one many other` (`many` is used for
   1 000 000; it usually repeats `other`); de, nl, tr and en `one other`. Exact selectors count
   only when they match every integer of a category (`=0` covers Arabic `zero`, `=1` covers
   German `one`, but not Russian `one`, which also matches 21). Extra categories, such as a `one`
   branch in Japanese, are allowed. A plural with only exact selectors and `other` is a numeric
   switch rather than grammatical number (`{totalPages, plural, =0 {…} other {…}}`); it is
   allowed where English uses the same switch for that argument.

There is no baseline of accepted exceptions: fix the translation (in Weblate or in the locale
file) instead.

The second half of `pnpm i18n:check` verifies that the client message scopes are up to date
(see below).

## Client message scopes

The root layout inlines the client message catalogue in every HTML document. Each route group
gets only the message paths that its client components can request:

| Scope     | Routes                                                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------ |
| `public`  | Home, entity lists and details, legal pages and history, category/tag, CMS Pages, `/s/*`, `/user/*`, … |
| `forms`   | `/forms` pages (the `public` catalogue includes it)                                                    |
| `auth`    | `/login`, `/account/…`, `/verify`, `/oauth/authorize/consent`, `/onboarding/…`, `/subscribe*`, …       |
| `account` | `/my` pages                                                                                            |
| `admin`   | `/admin` pages                                                                                         |
| `editor`  | `?edit=true` / `?view=edit` on routes that render an editor, `/campaigns/[id]`, `/editor-lab-local`    |

- A path has the scope of the App Router page that serves it. Paths that no route pattern
  matches, such as `/forms/team/about`, `/oauth/help` or `/admin/unknown`, are CMS Pages served by
  `app/(general)/[...slug]` (`public`, or `editor` with `?edit=true`).
- `lib/i18n/client-message-scope.ts` maps a path to its scope with the generated route table
  (`lib/i18n/client-message-routes.generated.ts`, matched by `client-message-route-match.ts` with
  App Router precedence). The server and the client both use it.
- `pnpm i18n:scopes` writes the route table and `lib/i18n/client-message-scopes.generated.ts`.
  The route table lists every page pattern with its scope (by first URL segment,
  `ROUTE_SCOPE_ROOTS`) and whether the page imports an `EDIT_MODE_MODULES` module. The script
  fails when the resolver disagrees with Next's route matching for any page pattern, its
  neighbours or `AMBIGUOUS_ROUTE_PROBES`. It maps every
  `app/**/page.tsx` to a scope, both as-is and with `?edit=true`. It then walks the imports of
  the page and of its ancestor layouts and error/not-found files. Every module that has
  `'use client'`, or that is imported by such a module, adds the namespaces of its
  `useTranslations('…')` calls. Server components read the full catalogue from
  `i18n/request.ts`, so they add nothing.
- Modules that a public route renders only for `?edit=true` are listed in `EDIT_MODE_MODULES`.
  They count toward `editor` only. A `useTranslations()` call whose namespace is not a string
  literal must be declared in `DYNAMIC_TRANSLATION_SOURCES`.
- `lib/i18n/client-message-scopes.test.ts` fails, with the import chain, when a client
  component requests a path that its scope does not ship. Without this check, the page would
  show raw keys.
- When client-side navigation enters a scope that the inlined catalogue does not cover,
  `ClientMessagesProvider` loads the complete catalogue for the locale (one cacheable chunk).
  For signed-in users, it prefetches that chunk while the browser is idle.

After you add a `useTranslations` call or a route, or move a component to another route, run
`pnpm i18n:scopes` and commit the generated files.
